## 1. 한 줄 요약

머더 미스터리 1회 세션은 **"브리핑(1회) → 캐릭터 배정·소개(1회) → 규칙 공지(1회) → [조사 라운드 루프: 단서 배포 + 알리바이/심문/변론] × N회 → 지목 투표(최소 1회, 재투표 가능) → 공개 블록(범인 공개 → 미션 자가 체크 → 단일 텍스트 엔딩) → 디브리프(1회)"** 의 구조를 가지며, 통상 2~3시간, 조사 라운드 횟수(N)는 업체·시나리오별로 **3 라운드 또는 6 라운드** 등으로 갈린다. 즉 **"라운드 개수 자체가 업계 표준이 아니며, 조사 구간은 선형이 아니라 루프"** 임을 설계 전제로 삼아야 한다.

## 2. 표준 단계 (보편 공식)

표는 **선형 단계(세션당 1회 발생)**와 **루프 블록(N회 반복 가능)**을 구분한다. 시간 비중은 2~3시간(≈150분) 세션 기준 **일반 추정치**로, 출처별 편차가 크다. "BYOD 자동화 후보" 열은 본 프로젝트의 설계 결정을 돕는 1차 판단.

### 세션 오프닝 (선형, 각 1회)

| # | 단계 | 목적 | 플레이어 행동 | GM의 전통적 역할 | 시간 비중 | BYOD 자동화 후보 |
|---|------|------|---------------|------------------|-----------|-------------------|
| 1 | **도입 (Intro / Briefing)** | 세계관·사건 개요 전달 | 도입 내레이션 청취 | 오프닝 낭독, 분위기 조성 | 5–10% (10–15분) | **Yes** — 텍스트/오디오 자동 재생으로 완전 대체 가능 |
| 2 | **캐릭터 배정 & 소개 (Character Intro)** | 역할 인식, 관계망 공유 | 캐릭터 정보 숙독, 공개 정보 발표 | 역할 분배, 숙지 시간 고지 | 10% (10–20분) | **Partial** — 배정·개인 정보 전달 Yes, 연기 자체는 No |
| 3 | **규칙 공지 (Rules Briefing)** | 진행 규칙·제한 설명 | 수동 청취 | 거짓말 허용 범위·공개 수준 공지 | ~5% (추정) | **Yes** — 인앱 튜토리얼 + JIT 맥락 힌트로 대체 가능 (OST Sol 2B 계열) |

### 조사 라운드 루프 (루프 블록 × N회)

**블록 전체 특성:** N회 반복. 반복당 내부 시퀀스는 시나리오가 선언. 흔한 배열은 `[단서 배포 → 알리바이/심문/변론]` 또는 `[알리바이 → 단서 배포 → 심문]` 순서. 라운드가 반복될 때 **이전 라운드의 단서·발언은 유지되고, 새 단서·새 목표·새 제약이 추가**되는 것이 업계 관용 (Night of Mystery의 "objective sheet 재배포", Red Herring Games의 6 라운드 중 라운드별 목표 차등). 루프 전체 시간 비중은 세션의 **55–75%** (90–135분)로 가장 크다.

| # | 단계 (루프 내부) | 목적 | 플레이어 행동 | GM의 전통적 역할 | 루프당 시간 | BYOD 자동화 후보 |
|---|------|------|---------------|------------------|-------------|-------------------|
| L1 | **알리바이/심문/변론 (Alibi · Investigation · Final Statements)** | 라운드별 목표(동기/수법/반론 등) 규명 | 자유 대화, 공개 정보 교환, 심문, **밀담([§2.5 모듈](#25-밀담-모듈-private-conversation-module))**, 최종 변론 | 자연 진행 허용, 시간 경고, 이탈 감시 | 15–25% × N | **No** — 대면 상호작용 본질. 앱은 타이머·라운드별 프롬프트·밀담 상태 공지(§2.5)만 보조 |
| L2 | **증거·단서 배포 (Clue Distribution)** | 라운드별 새 단서 공개 | 단서 해석, 재질문 | 라운드마다 1–2개 단서 공개 | L1 시간에 포함/교차 | **Yes** — 조건·시간·라운드 번호에 따라 자동 해금. 가장 강력한 자동화 영역 |

**루프 종료 조건:** 시나리오 메타가 선언. 대표 패턴 — (a) 고정 횟수 `N=3` 또는 `N=6`, (b) 특정 단서·트리거 도달 시 종료, (c) 호스트/시나리오 타이머 경과 시 종료. 본 프로젝트 엔진은 **최소한 (a) 고정 횟수를 MVP 스코프로** 보장한다 ([§7 POC 매핑](#7-본-프로젝트-poc-매핑-downstream-연결) 참조).

### 세션 클로징 (선형, 투표는 재투표 가능)

| # | 단계 | 목적 | 플레이어 행동 | GM의 전통적 역할 | 시간 비중 | BYOD 자동화 후보 |
|---|------|------|---------------|------------------|-----------|-------------------|
| 8 | **지목 투표 (Accusation / Vote)** | 범인 지목 및 최후 변론 | 투표지 작성 | 투표지 수거·집계 | 5–10% (10분) | **Yes** — 앱 투표는 집계·이력까지 완전 자동화. **재투표 지원 필요**(일부 시나리오는 동점 시 재투표 또는 라운드 추가) |
| 9-A | **범인 공개 (Reveal)** | 누가 범인이었는지 내레이션 | 수동 청취, 반응 | 해답 낭독 | ~2% (5분) | **Yes** — 자동 재생 |
| 9-B | **미션 달성 자가 체크 (Mission Self-Check)** | 각 캐릭터의 숨겨진 미션을 플레이어 본인이 ✓/✗ 체크 | 본인 카드에서 미션 결과 입력 | 없음 (앱이 UI 제공) | ~2% (3–5분) | **Partial** — UI는 앱, 판정은 사람 |
| 9-C | **단일 텍스트 엔딩 재생 (Ending)** | 시나리오당 1개의 단일 텍스트 엔딩 자동 재생 | 수동 청취, 반응 | 없음 | ~3% | **Yes** — 자동 |
| 10 | **디브리프 (Debrief / Wrap-up)** | 복선 회수 해설, 사회적 회고 | 회고·잡담 | 전체 설정서 종합 설명 | ~5% | **Partial** — 복선 해설 자동화 가능, 사회적 회고는 No |

### 설계 전제 요약

- **앱이 완전 자동화(Yes):** 1·3·L2·8·9-A·9-C → "메타 부담" 층 (OST Opp 2 해결 표적)
- **앱이 부분 자동화(Partial):** 2·9-B·10 → 프롬프트·타이머·자가 체크 UI·로그로 보조
- **앱이 자동화하지 않음(No):** L1 → 대면 상호작용의 본질 구간. 루프가 N회 반복돼도 이 원칙은 유지
- **모든 데이터에 "몇 라운드째인지"가 꼬리표로 붙는다:** 루프 안에서 발생하는 모든 이벤트·프롬프트·목표·단서 기록에는 "이게 몇 번째 라운드에서 일어난 일인가"가 처음부터 함께 저장된다. 예컨대 도움말을 누른 기록이 남을 때 "몇 라운드째에 눌렀는지"가 같은 줄에 기록되어, 나중에 "3라운드에서 도움말을 몇 번 눌렀지?"를 시간 역산으로 맞추지 않고 바로 꺼내 볼 수 있어야 한다. 텔레메트리 분석과 카드 UI 모두 이 라운드 번호를 축으로 돌아간다
- **라운드 간 상태 승계:** 라운드가 바뀌어도 **이전 라운드의 단서·발견·발언은 폐기되지 않는다.** 새 라운드는 기존 위에 정보를 더 얹는 것이지 처음부터 다시 시작하는 것이 아님
- **세션 클로징은 3단계 자동 체인(9-A → 9-B → 9-C) 후 디브리프(10):** 9-C(단일 텍스트 엔딩)가 "클로저(closure) 생성"을 담당
- **미션 자가 체크(9-B)는 "경쟁이 아닌 재미"의 장치:** 조작 가능하지만 본 게임은 순위 경쟁이 아니라 "어떤 이야기를 함께 완성할지"에 가까움. 앱은 조작 감지·제재를 하지 않고 본인 회상용 입력으로만 사용

## 2.5 밀담 모듈 (Private Conversation Module)

**위치:** 루프 블록 L1의 **선택적 하위 행동**으로만 존재. 오프닝(1·2·3)·L2·클로징(8·9)·디브리프(10)에는 신청 경로 자체가 노출되지 않는다.

### 2.5.1 정의

밀담은 세션 내 모든 플레이어가 아니라 **신청자가 지목한 소수의 상대와만 따로 나누는 대화**다. 전체 토론에서는 나오지 못할 의심·동맹·정보 교환을 허용해 다인 플레이의 전략적 깊이를 만든다. 한국 관용상 6인+ 시나리오에서 주로 사용되며, 5인 이하에선 "자유 대화"와 사실상 분리되지 않는다 (출처: 나무위키 "머더 미스터리(게임)", 보드라이프 입문 가이드). **입문자에게는 소외감·난이도 상승 요인**으로 지목되어 있어 본 모듈은 기본 비활성을 권고한다.

### 2.5.2 시나리오 메타 선언

| 필드 | 타입 | 기본값 | 설명 |
|---|---|---|---|
| `allow_private_talk` | boolean | **false** | 이 시나리오에서 밀담 신청 UI를 노출할지 여부 |
| `max_private_talks_per_round` | integer? | null (무제한) | 한 라운드당 같은 플레이어가 신청할 수 있는 밀담 횟수 상한 (선택) |
| `private_talk_log_visibility` | boolean | **true** | 밀담의 "누가 누구와·몇 라운드" 전원 배너 및 타임라인 공개 여부. `false`면 밀담 상태는 참여자만 인지. ACL과 텔레메트리 수집에는 영향 없음 — 플레이어 UI 가시성만 제어 |

기본값 off. 시나리오 저자가 의도적으로 on한 시나리오에서만 모듈이 활성.

### 2.5.3 참여 구성

- **인원 상한 없음.** 신청자가 대상 n명을 지목 → 각 대상이 수락/거절 선택 → **수락자만 참여 성립**. 수락자가 0명이면 밀담 불성립으로 자동 소멸
- **거절 이유 입력 없음** — 대면 관례와 일관. 거절자가 존재한다는 사실 자체의 공개 범위는 열린 질문 (PRD §8 참조)
- **배타적 참여:** 한 사람은 동시에 **하나의 밀담**에만 속한다. 이미 밀담 중인 사람에게는 신규 신청이 도착하지 않거나 "통화 중"으로 표시

### 2.5.4 앱의 역할 (의도적으로 좁은 스코프)

앱이 제공하는 유일한 가치는 **"누가 누구와 밀담 중인가"의 실시간 공지**다. 구체적으로:

- 신청·수락·거절·종료의 흐름 관리 (상태 기계)
- 모든 플레이어에게 보이는 **'밀담 중' 상태 배너/리스트** (참여자 목록 + 시작 시각)
- 이벤트 텔레메트리 기록

앱이 **제공하지 않는** 것:

- 밀담 참여자 전용 **비공개 채팅/음성 채널** — 실제 대화는 대면으로. 이는 본 제품의 "같은 공간 대면 가치 보존" 원칙과 정합. **단, 이와 별개로 "아이템(단서 카드·정보물)의 상태 변경 행위(교환·전체 공유·부분 공유)"는 PRD §5.2의 아이템 상태 모듈에서 앱의 1급 기능으로 제공된다** — 메타데이터는 전원 공개(시나리오 저자 플래그로 조정 가능), 콘텐츠는 행위별 ACL. "대화 채널 없음" 원칙은 '말'에만 적용되며 '정보물'에는 적용되지 않는다

### 2.5.5 종료 조건

1. **참여자 중 누구나 '종료' 버튼** → 즉시 종료
2. **라운드 경계 도달** → 해당 L1 종료 시 자동 종료 (L2/다음 라운드로 넘어가면 자동 해산)
3. **(선택) 지속시간 상한** — 시나리오 저자가 상한을 선언한 경우, 경과 시 자동 종료

### 2.5.6 경험 비대칭 리스크 경고

> 밀담은 "머더 미스터리의 꽃"으로 꼽히는 동시에, **경험 적은 플레이어에게 난이도와 소외감을 유발**할 수 있다 (나무위키, 보드라이프). 따라서 본 프로젝트는 `allow_private_talk` 기본값을 false로 두고, 활성 시에도 "누가 누구와 밀담 중"이 전원에게 보이도록 하여 "내가 모르는 곳에서 내 얘기가 오간다"는 소외감을 최소화한다.

## 3. 캐릭터 카드 표준 구성 요소

### 필수 필드 (다수 출처 공통)

- **이름 (Name)**
- **배경·직업 (Background / Occupation)**
- **피해자·타 인물과의 관계 (Relationship)**
- **동기 (Motive)** — 실제 동기이든 "의심받을 이유"든
- **알리바이 (Alibi)**
- **비밀 (Secret / "skeletons in closet")** — 살인 무관 비밀까지 포함
- **목표·미션 (Objective)** — 라운드별로 분기 가능

### 선택 필드

- 나이(Age), 성격(Personality), 친구/적 관계(Friends/Enemies)
- 의상·분장 가이드(Costume suggestions)
- **캐치프레이즈·말투 가이드 (Catchphrase / Voice)** ← **본 프로젝트 POC 핵심 필드**
- 히든 미션(Hidden Mission) — 한국 시나리오에서 빈번
- 레드 헤링(Red Herrings)

### 본 프로젝트 POC 매핑

업계에서는 선택 필드로 분류되는 "캐치프레이즈·말투 가이드"를 **본 프로젝트에서도 시나리오 저자 재량의 선택 필드**로 둔다. 시나리오 저자가 채워 넣는 경우, 카드 UI는 이 필드를 상시 접근 가능 위치(카드 상단)에 일관 노출해 "역할 몰입 자유도"(2차 가치)의 그릇 역할을 한다 (PRD §4.3·§7 Epic 2).

**추가 필수 필드 (엔딩 모델용):**

- **미션(Mission) / 본인 승리 조건** — 각 캐릭터 고유의 숨겨진 목표. *"당신은 누구에게도 의심받지 않으면 달성"*, *"X와 동맹을 맺으면 달성"* 같은 **본인 시점 미션**. 시나리오별 캐릭터당 **1–3개** 제안 (상한은 시나리오 저자 재량, MVP는 느슨한 가이드)
- 각 미션은 구조적으로 `label`(짧은 이름), `description`(공개 시점 설명) 속성을 가짐
- 미션 공개 시점: **단계 9-B(공개 단계 내부)**. 이전까지는 플레이어 본인에게도 카드에 숨겨져 있어도 되고, 일부 시나리오는 라운드 중에 공개해도 됨 (시나리오 저자 선택)
- 달성 판정: **본인 자가 체크 (✓/✗)**. 앱은 판정 안 함. "경쟁이 아닌 재미" 원칙에 따라 조작 감지 없음

## 4. 대표 예시

### 예시 A — Hunt a Killer (미국, 구독 박스)

- **형태:** 물리 박스 구독 서비스
- **구조:** 1 시즌 = 6개 에피소드(= 박스), 박스 하나가 미션 하나
- **캐릭터 수:** 해당 없음 — **1~다수 플레이어용 독립 서사 조사 게임** (파티 형식 아님)
- **플레이 시간:** 박스당 핵심 약 30분, 부가 콘텐츠 포함 시 더 길어짐
- **특이 메커니즘:** 월 1회 박스 배송의 연속 서사, 물리 소품(검시 보고서·진술서) 중심, **GM 없는 비동기 플레이**

**본 프로젝트에 주는 시사:** 비동기 개인 조사 서사는 본 제품 포지션과 다르지만, "물리 소품 없이 앱이 그 역할을 대신한다"는 단서 배포(5번 단계) 자동화 가능성을 뒷받침.

### 예시 B — Night of Mystery (미국, 다운로드 PDF 키트)

- **형태:** 테마별 PDF 키트 다운로드형
- **구조:** **8 단계 진행** — 도착 → 호스트 도입 → 1차 목표 배포 → 살인 이벤트 → 2차 목표 → 증거 공개 → 해답 공개 → 어워드
- **캐릭터 수:** 시나리오별 상이 (원문에 일반화 수치 없음)
- **플레이 시간:** 원문에 시간 명시 없음
- **특이 메커니즘:** **라운드별 "objective sheet" 다중 배포**, **어워드 인증서** 포함

**본 프로젝트에 주는 시사:** "라운드별 목표지 교체 배포"라는 구조는 단계 5(단서 배포)의 자동화 요구를 명료하게 해준다 — 라운드 트리거로 객체가 교체되는 모델.

### 예시 C — 한국 "크라임씬" 유형 (오프라인 보드게임/세트장)

- **형태:** 오프라인 보드게임·세트장
- **구조:** 캐릭터 선택 → 도입 → 증거 조사 → 토론 → 투표 → 진실 공개
- **캐릭터 수:** 시나리오별 **4–5명** (예: "Y의 장례식" 4인, "목 베는 마을" 5인)
- **플레이 시간:** 최소 2시간 이상
- **특이 메커니즘:** **거짓말 허용 범위**(범인만 vs 전원)와 **증거 공개 방식**(전원 공개 vs 공유 비공개)이 시나리오별로 달라지는 것이 장르 고유 설계 변수

**본 프로젝트에 주는 시사:** POC의 캐릭터 수(3–4명)는 국내 크라임씬 유형의 하단(4–5명)과 겹치면서 **약간 더 가볍다**. 국내 사용자의 관용 구조와 큰 충돌 없음. "거짓말 허용 범위"와 "증거 공개 방식"은 **시나리오 단위 파라미터**로 엔진이 지원해야 한다.

## 5. 진행 방식 비교 (GM-주도 vs 스크립트-플렉스 vs 앱 BYOD)

머더 미스터리는 **메타 부담을 누가 짊어지는가**에 따라 크게 세 계열로 나뉜다.

| 축 | GM-주도 키트 | 스크립트-플렉스 (GM 없음) | 디지털 앱 BYOD (본 제품) |
|-----|---------------|---------------------------|----------------------------|
| 대표 플랫폼 | Night of Mystery, Masters of Mystery, 한국 크라임씬 | Red Herring Games 등 | Mystery Night App, MysteryWild, **본 제품** |
| 메타 부담 주체 | **호스트 1인에 집중** | 호스트가 역할 겸임 — 부담 감소하지만 사라지지 않음 | **앱으로 이전** — 호스트 플레이어화 |
| 자동화되는 단계 | 거의 없음 | 라운드 스크립트 낭독 구조화 | **1·3·5·8·9** (완전) + **2·6·7·10** (부분) |
| 사람에게 남는 단계 | 4·6·7·10 (상호작용) | 동일 + 라운드 경계 주도 | **4** (알리바이 대면 대화) 위주, 2·6·7·10은 앱이 보조 |
| 대표 실패 모드 | 호스트 번아웃, 규칙 오인 | 호스트의 "역할 몰입 vs 진행" 충돌 | 오프라인 대화와 앱 상태 동기화 실패, 앱 주시가 몰입 파괴 리스크 |

**핵심 통찰:** 세 계열 모두 **루프 블록 내부 L1(알리바이·심문·변론, 대면 대화)은 사람의 영역**으로 남기고, **L2(단서 배포)·투표·공개는 자동화**한다. 즉 BYOD 자동화가 아무리 공격적이어도 "같은 공간 대면 대화"라는 가치 중심은 보존된다. 동시에, BYOD 앱은 **"라운드가 반복되는 블록 자체"를 시나리오마다 갈아끼울 수 있는 설정값으로 다뤄야 한다** — 단계 순서를 코드에 고정해 버리면 3 라운드/6 라운드/8 단계 키트 모두를 담을 수 없다. 즉 "라운드 수 · 라운드 안의 진행 순서 · 종료 조건"을 시나리오마다 바꿔 넣을 수 있게 만들어야 한다.

## 6. 이탈 지점 관련 증거

### 뒷받침 (규칙·초반 단계 혼란이 이탈 유발이라는 가설 지지)

- Red Herring Games 업계 경험담: **"규칙이 너무 복잡해 사람들이 차라리 죽기를 원하는"** 실패 사례가 공개적으로 언급됨
- 한 호스트 리뷰: *"대부분 손님이 머더 미스터리가 처음이었고, 정확히 뭘 해야 하는지 매우 혼란스러워했으며, 많은 사람이 방을 나가 캐릭터를 찾아다니려 했다"*
- 업계 일반 관찰: *"거의 모든 호스트가 게임이 너무 혼란스럽거나 지루하거나 빠르거나 길까 봐 걱정한다"*

### 반박/뉘앙스

- Megan's Mysteries 입장: **중반(Round 2 전후)의 혼란은 의도된 설계**. *"Halfway confusion usually means the story is working."* → 모든 혼란을 "이탈 위험"으로 해석하지 말 것.
- 다만 이 입장은 **규칙·캐릭터 소개 같은 초반 단계의 혼란은 다루지 않음** → 본 프로젝트의 "규칙 공지 이탈" 가설과 **직접 충돌하지 않음**.

### 정량 증거

- **공개 정량 데이터 없음.** "규칙 공지 단계 이탈률 %", "Round 1 vs Round 3 체류율" 같은 수치는 리서치 범위의 공개 웹 자료에서 확인 불가.

### 결론

> **정성 증거는 "규칙 복잡도 + 초반 방향성 상실"이 혼란의 주 요인**임을 시사한다. 단, 규칙 공지 단계 자체로 이탈을 귀속할 정량 근거는 없고, 중반 혼란은 장르 고유 특성이라는 반론이 존재한다.

## 7. 본 프로젝트 POC 매핑 (Downstream 연결)

| Game Flow 항목 | 대응 OST 항목 | PRD 에픽 영향 |
|----------------|----------------|----------------|
| 단계 1·3·L2·8·9 (완전 자동화 후보) | Opp 2 (메타 부담 주의력 분산) — Sol 2A/2B/2C | **Epic 1: 시나리오 진행 엔진** — 씬 전환·단서 배포·투표 집계·공개 재생 |
| 캐릭터 카드 "말투 가이드" 선택 필드 | Opp 1 (역할 몰입 자유도) | **Epic 2: 캐릭터 카드 UI + 말투 가이드** — 시나리오 저자가 채워 넣은 경우 상시 접근 위치에 일관 노출 |
| **조사 라운드 루프(N회) + "모든 데이터에 라운드 번호 꼬리표"** | Opp 2 전면 | **Epic 1:** 엔진이 루프 블록·종료 조건·라운드별 설정값(단서·목표·프롬프트)을 시나리오 설정으로 받음. 모든 이벤트·기록에 "몇 번째 라운드의 일인지" 필드가 함께 저장됨 |
| 라운드 간 상태 승계 (단서·발언 유지) | 시나리오 제작 요구사항 | Epic 1 데이터 모델: 라운드가 바뀌면 기존 정보 위에 새 정보를 얹는 구조(쌓아 올리기)이지, 처음부터 다시 시작하는 구조 아님 |
| L1 (사람 영역 보존) | Phase 3 제품 설계 전제 #4 (BYOD 단일 포지션) | **모든 에픽의 공통 제약** — 알리바이/심문/변론 단계에서는 앱이 전면에 나서지 않음 (몰입 파괴 역설 회피). N회 반복돼도 유지 |
| 라운드 개수의 업계 비표준성 | 시나리오 단위 파라미터 필요 | Epic 1의 엔진은 **3 라운드·6 라운드·8 단계 키트**를 모두 담을 수 있는 일반화 구조여야 함 — 루프 종료 조건(a)(b)(c) 중 최소 (a) 고정 N 지원 |
| 투표 재투표 시나리오 | — | Epic 1: 투표는 **같은 사람이 실수로 두 번 눌러도 한 번만 집계되며, 동점 시 자동으로 재투표 라운드가 열리는** 구조를 지원 |
| **단계 9-B/9-C 세분화 — 미션 자가 체크 + 단일 텍스트 엔딩** | "범인 찾기가 유일한 목적이 아님" | **Epic 1:** 단일 텍스트 엔딩 자동 재생 / **Epic 2:** 카드 `mission` 필드 (`label`/`description`) + 공개 단계 자가 체크 UI + 결과·엔딩 keepsake 앱 내 표시 |
| "거짓말 허용 범위 / 증거 공개 방식" 시나리오 파라미터 (한국 크라임씬) | 시나리오 제작 요구사항 | Epic 1: 엔진이 시나리오 메타 필드로 노출해야 할 설정 |
| **§2.5 밀담 모듈 — 시나리오 플래그 + 'L1에서만 활성' + '밀담 중' 상태 공지** | 다인 자유도 (Opp 1 보조 축) | **Epic 1:** 밀담 상태 기계(대기→진행→종료) + 전체 공지 브로드캐스트 + L1 페이즈 조건부 UI 노출. **Epic 2:** 세션 화면의 '밀담 중' 리스트·배너 |
| **아이템 상태 모듈 (교환·전체 공유·부분 공유) — 메타 공개(저자 플래그로 조정) + ACL(monotonic)** | Opp 1 (역할 몰입·자유도) + Opp 2 (메타 부담 경감: 기억 관리를 앱이 흡수) | **Epic 1:** 상태 기계·ACL·실시간 전원 배너·이벤트 타임라인·4개 로그 공개 플래그. **Epic 2:** 카드의 소유/접근권 섹션 분리 + Keepsake 본인 참여 이력 |

## 조사 한계

1. **정량 이탈 데이터 없음** — 단계별 이탈률·체류시간 관련 공개 통계 미확보. Hunt a Killer·Night of Mystery 내부 데이터 비공개.
2. **Reddit 원문 스레드 확인 제한** — r/murdermystery, r/rpg 관련 1차 스레드 URL 확보 실패. 블로그·업체 가이드 위주 인용.
3. **시간 비중의 추정성** — 라운드 수가 업체별로 3/6 등으로 상이하여 2섹션의 %는 일반 추정. 업체·시나리오별 편차 큼.
4. **국내 크라임씬 외 한국 머더 미스터리 관용** — 보드라이프 일부 문서 접근 차단(401/403)으로 간접 인용. 국내 시장 구조는 별도 심층 조사 필요.
5. **밀담의 공식 규격 부재** — 한국 관용상 밀담의 **인원 상한·시간 제한·거절 공개 범위**에 대한 표준화된 정의는 확인되지 않았다. "6인+에서 주로 쓴다" "원하는 사람끼리 따로" 수준의 서술이 최대치이며, 세부 파라미터는 시나리오 저자 재량에 맡겨진다. 본 §2.5는 이 공백을 **앱 설계에 필요한 최소 파라미터 세트**로 임의 충전한 것이며, 업계 표준 주장이 아님.
